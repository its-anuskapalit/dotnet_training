This page teaches normalization in the simplest way: why it exists, what each normal form means, and how to fix tables using SQL Server queries.

1) What is Normalization?

Normalization is a set of rules to design tables so that data is stored in a clean and correct way.

In one line: Normalization means split data into logical tables and connect them using keys so you avoid duplicates and mistakes.

Think Like This (Real Life)

Imagine you are saving customer orders in Excel. If you write the customer name, address, product names, and prices repeatedly in every row, after some days you will make mistakes.

Bad (messy): One big sheet with repeated values OrdersSheet(OrderId, CustomerName, CustomerPhone, CustomerAddress, Product1, Product2, Product3, ...) Good (normalized): Separate sheets + relationships Customers(CustomerId, Name, Phone, Address) Orders(OrderId, CustomerId, OrderDate) OrderItems(OrderId, ProductId, Qty, UnitPrice) Products(ProductId, Name, Price)
Beginner Tip: Normalization is not about “more tables for no reason”. It’s about putting each fact in the correct place.

2) Problems Normalization Fixes (Anomalies)

When your table is not normalized, you face 3 common issues:

Problem What it means (super simple) Real example
Update Anomaly You update the same info in many rows → you miss one row → data becomes wrong. Customer phone changed, but you updated only 3 orders out of 10.
Insert Anomaly You cannot add a piece of data because another piece is missing. You want to add a new product, but your table requires an order to exist.
Delete Anomaly Deleting a row deletes important info unintentionally. Deleting the last order of a customer deletes customer details too.

4) Un-Normalized Example (Why it’s bad)

Let’s see the exact problems with this table.

Problem A: Can't query products properly

Bad filtering 
-- Want: all orders that contain 'Mouse'
-- This is not reliable because it depends on text format.
SELECT * 
FROM dbo.Order_Bad
WHERE ProductNames LIKE '%Mouse%';
Why bad? Because "Mouse Pad" will also match. Also spacing/commas can break results.

Problem B: Update anomaly

Customer phone update 
-- Customer phone changed. You must update multiple rows.
UPDATE dbo.Order_Bad
SET CustomerPhone = '9000000000'
WHERE CustomerName = 'Arjun Kumar';
Why risky? If one row is missed, same customer will show two phone numbers.

5) First Normal Form (1NF)

Rule Each column should have single (atomic) values. No lists, no commas.

1NF = One cell = One value
Example: Instead of "Mouse, Keyboard" in one cell, store as two rows in an OrderItems table.

Convert our bad table into 1NF

We will create proper tables: Customers, Orders, Products, OrderItems.

1NF Tables (Customers, Orders, Products, OrderItems) 
-- Clean old tables if re-running
IF OBJECT_ID('dbo.OrderItems', 'U') IS NOT NULL DROP TABLE dbo.OrderItems;
IF OBJECT_ID('dbo.Orders', 'U') IS NOT NULL DROP TABLE dbo.Orders;
IF OBJECT_ID('dbo.Products', 'U') IS NOT NULL DROP TABLE dbo.Products;
IF OBJECT_ID('dbo.Customers', 'U') IS NOT NULL DROP TABLE dbo.Customers;
GO

CREATE TABLE dbo.Customers
(
    CustomerId     INT IDENTITY(1,1) PRIMARY KEY,
    CustomerName   VARCHAR(100) NOT NULL,
    CustomerPhone  VARCHAR(20)  NOT NULL,
    CustomerCity   VARCHAR(50)  NOT NULL
);

CREATE TABLE dbo.Orders
(
    OrderId     INT PRIMARY KEY,
    OrderDate   DATE NOT NULL,
    CustomerId  INT NOT NULL,
    CONSTRAINT FK_Orders_Customers
      FOREIGN KEY (CustomerId) REFERENCES dbo.Customers(CustomerId)
);

CREATE TABLE dbo.Products
(
    ProductId   INT IDENTITY(1,1) PRIMARY KEY,
    ProductName VARCHAR(100) NOT NULL UNIQUE,
    ListPrice   DECIMAL(10,2) NOT NULL
);

CREATE TABLE dbo.OrderItems
(
    OrderId   INT NOT NULL,
    ProductId INT NOT NULL,
    Qty       INT NOT NULL,
    UnitPrice DECIMAL(10,2) NOT NULL,

    CONSTRAINT PK_OrderItems PRIMARY KEY (OrderId, ProductId),
    CONSTRAINT FK_OrderItems_Orders FOREIGN KEY (OrderId) REFERENCES dbo.Orders(OrderId),
    CONSTRAINT FK_OrderItems_Products FOREIGN KEY (ProductId) REFERENCES dbo.Products(ProductId)
);
GO

✅ Verify (Join Query) — See full order with items
Join to view data 
SELECT
    o.OrderId,
    o.OrderDate,
    c.CustomerName,
    c.CustomerPhone,
    c.CustomerCity,
    p.ProductName,
    oi.Qty,
    oi.UnitPrice,
    (oi.Qty * oi.UnitPrice) AS LineTotal
FROM dbo.Orders o
JOIN dbo.Customers c ON c.CustomerId = o.CustomerId
JOIN dbo.OrderItems oi ON oi.OrderId = o.OrderId
JOIN dbo.Products p ON p.ProductId = oi.ProductId
ORDER BY o.OrderId;
Now we are in 1NF! Products are no longer stored as comma-separated lists. Each product is one row in OrderItems.

6) Second Normal Form (2NF)

Rule Must be in 1NF + no partial dependency (mainly happens when you use a composite key).

Simple meaning: If your table key is (A, B), then every non-key column must depend on both A and B, not only A.

Beginner Example (Bad 2NF)

Suppose someone stores product name inside OrderItems (bad idea):

Bad table showing 2NF issue 
-- ❌ Bad design (for learning)
-- Key is (OrderId, ProductId), but ProductName depends only on ProductId.
CREATE TABLE dbo.OrderItems_Bad2NF
(
    OrderId     INT NOT NULL,
    ProductId   INT NOT NULL,
    ProductName VARCHAR(100) NOT NULL, -- ❌ depends only on ProductId
    Qty         INT NOT NULL,
    UnitPrice   DECIMAL(10,2) NOT NULL,
    CONSTRAINT PK_OrderItems_Bad2NF PRIMARY KEY (OrderId, ProductId)
);
Problem: If ProductName changes (e.g., "USB Hub" becomes "USB Hub 3.0"), you must update many rows. That is an update anomaly.

Fix for 2NF (Correct Design)

Put product details into Products. Keep only ProductId in OrderItems. (We already did this. ✅)

TableStoresDepends on
ProductsProductName, ListPriceProductId
OrderItemsQty, UnitPrice(OrderId, ProductId)
Shortcut memory: 2NF usually means “remove repeated item details from line-item table”.

7) Third Normal Form (3NF)

Rule Must be in 2NF + no transitive dependency.

Simple meaning: A non-key column should not depend on another non-key column. Everything should depend only on the key.

Beginner Example (Bad 3NF)

Let’s say you store City and State together wrongly in Customers:

Bad 3NF example 
-- ❌ Bad: State is determined by City (for many systems)
-- CustomerId -> City -> State   (transitive dependency)
CREATE TABLE dbo.Customers_Bad3NF
(
    CustomerId    INT IDENTITY PRIMARY KEY,
    CustomerName  VARCHAR(100) NOT NULL,
    City          VARCHAR(50) NOT NULL,
    State         VARCHAR(50) NOT NULL
);
Problem: If you type "Bengaluru" with State as "Tamil Nadu" by mistake, your data becomes incorrect. You might store different states for the same city.

Fix for 3NF (Simple & Practical)

Create a Cities table and reference it (good for big systems). For small systems, you may keep City as text, but for learning, we will normalize it.

3NF Fix: Cities master table 
IF OBJECT_ID('dbo.Cities', 'U') IS NOT NULL DROP TABLE dbo.Cities;
GO

CREATE TABLE dbo.Cities
(
    CityId   INT IDENTITY(1,1) PRIMARY KEY,
    CityName VARCHAR(50) NOT NULL UNIQUE,
    State    VARCHAR(50) NOT NULL
);

-- Add a CityId column to Customers (demo approach)
ALTER TABLE dbo.Customers
ADD CityId INT NULL;

-- Insert city master data
INSERT INTO dbo.Cities(CityName, State)
VALUES
('Chennai', 'Tamil Nadu'),
('Bengaluru', 'Karnataka');

-- Update existing customers with CityId (simple demo)
UPDATE c
SET CityId = ci.CityId
FROM dbo.Customers c
JOIN dbo.Cities ci ON ci.CityName = c.CustomerCity;

-- Now you can optionally remove CustomerCity text column (optional for demo)
-- ALTER TABLE dbo.Customers DROP COLUMN CustomerCity;

-- Add FK
ALTER TABLE dbo.Customers
ADD CONSTRAINT FK_Customers_Cities
FOREIGN KEY (CityId) REFERENCES dbo.Cities(CityId);
✅ Verify: Show customers with City + State (Join)
Verify Join 
SELECT
  c.CustomerId,
  c.CustomerName,
  c.CustomerPhone,
  ci.CityName,
  ci.State
FROM dbo.Customers c
JOIN dbo.Cities ci ON ci.CityId = c.CityId
ORDER BY c.CustomerId;
Now we are in 3NF: City and State facts live in one place (Cities), so data stays consistent.

8) BCNF (Simple View)

BCNF is a stronger version of 3NF. For beginners, remember this:

BCNF idea: If a column determines another column, the determining column must be a candidate key.

Mini Example (Concept Only)

Table: Enrollment(StudentId, CourseId, Instructor) If a rule says: CourseId -> Instructor (each course has exactly one instructor) Then Instructor should NOT be inside Enrollment, because it depends on CourseId, not on (StudentId, CourseId). Fix: Courses(CourseId, Instructor) Enrollment(StudentId, CourseId)
Beginner shortcut: If you see a rule like “X decides Y”, put (X, Y) in a separate table unless X is already a key of that table.

9) Real-Time Mini Design (E-Commerce Style)

Here is a tiny real-world design you can use in projects (Orders, Customers, Products). This is the normalized structure.

Customers( CustomerId, Name, Phone, CityId ) Cities( CityId, CityName, State ) Products( ProductId, ProductName, ListPrice ) Orders( OrderId, OrderDate, CustomerId ) OrderItems( OrderId, ProductId, Qty, UnitPrice ) Payments( PaymentId, OrderId, Mode, Amount, PaidOn )
📌 Bonus: “Common beginner reporting queries”
1) Total amount per order 
SELECT
  o.OrderId,
  SUM(oi.Qty * oi.UnitPrice) AS OrderTotal
FROM dbo.Orders o
JOIN dbo.OrderItems oi ON oi.OrderId = o.OrderId
GROUP BY o.OrderId
ORDER BY o.OrderId;
2) Customer wise total spending 
SELECT
  c.CustomerName,
  SUM(oi.Qty * oi.UnitPrice) AS TotalSpent
FROM dbo.Customers c
JOIN dbo.Orders o ON o.CustomerId = c.CustomerId
JOIN dbo.OrderItems oi ON oi.OrderId = o.OrderId
GROUP BY c.CustomerName
ORDER BY TotalSpent DESC;
3) Top selling products 
SELECT TOP 5
  p.ProductName,
  SUM(oi.Qty) AS TotalQty
FROM dbo.Products p
JOIN dbo.OrderItems oi ON oi.ProductId = p.ProductId
GROUP BY p.ProductName
ORDER BY TotalQty DESC;
Real-time learning: Normalization makes reporting easier because each table has one clear purpose.

Exercise Set C: Normalize a table (real-world)

You are given a “bad” table: Employee_Bad(EmpId, EmpName, DeptName, DeptHead).
Tasks:

  1. Explain why this breaks 3NF (hint: DeptName → DeptHead).
  2. Create 2 tables: Departments and Employees with FK.
  3. Insert sample data and show a join query.
✅ Sample Solution (Set C)
Solution SQL 
IF OBJECT_ID('dbo.Employees','U') IS NOT NULL DROP TABLE dbo.Employees;
IF OBJECT_ID('dbo.Departments','U') IS NOT NULL DROP TABLE dbo.Departments;
GO

CREATE TABLE dbo.Departments(
  DeptId   INT IDENTITY PRIMARY KEY,
  DeptName VARCHAR(60) NOT NULL UNIQUE,
  DeptHead VARCHAR(60) NOT NULL
);

CREATE TABLE dbo.Employees(
  EmpId   INT IDENTITY PRIMARY KEY,
  EmpName VARCHAR(80) NOT NULL,
  DeptId  INT NOT NULL,
  CONSTRAINT FK_Emp_Dept FOREIGN KEY(DeptId) REFERENCES dbo.Departments(DeptId)
);

INSERT INTO dbo.Departments(DeptName, DeptHead) VALUES
('IT','Suresh'),
('HR','Meena');

INSERT INTO dbo.Employees(EmpName, DeptId) VALUES
('Arun', (SELECT DeptId FROM dbo.Departments WHERE DeptName='IT')),
('Divya', (SELECT DeptId FROM dbo.Departments WHERE DeptName='HR')),
('Rakesh', (SELECT DeptId FROM dbo.Departments WHERE DeptName='IT'));

SELECT e.EmpId, e.EmpName, d.DeptName, d.DeptHead
FROM dbo.Employees e
JOIN dbo.Departments d ON d.DeptId = e.DeptId
ORDER BY d.DeptName, e.EmpName;

11) Quick Revision Sheet

Normal FormEasy RuleCommon Fix
1NF One cell = One value (no lists, no repeating groups) Create a child table (e.g., OrderItems) for multiple values
2NF No partial dependency on composite key Move “product details” to Products table
3NF No non-key → non-key dependency (no transitive dependency) Create master tables (Cities, Departments, etc.)
BCNF Every determinant must be a candidate key Split tables when business rules violate keys
